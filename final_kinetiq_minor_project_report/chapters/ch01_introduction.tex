\chapter{INTRODUCTION}

\section{Background and Motivation}
Wearable devices provide continuous physiological observations, but companion-app screens are not automatically current or validated at a secondary interface. Transmission latency, packet loss, caching, and connection drops frequently separate an upstream capture from downstream display, risking misleading users. The developed wellness mirror system addresses this integration challenge through explicit provenance, freshness tracking, and contract validation.

The implementation connects a Huawei Band 6 and Huawei Health data pipeline to a laptop-based mirror interface via a local Android accessibility relay and authenticated receiver. Android accessibility services observe UI node hierarchies under user-granted permissions \cite{androidAccessibility}, avoiding unsupported claims of a direct Huawei Band API. The system simultaneously incorporates a native FreeRTOS v11 control lane using virtual tasks, queues, and mutexes \cite{freertosQueues,freertosMutex} to generate deterministic, inspectable synthetic telemetry when wearable connectivity is absent, ensuring synthetic control states are never presented as genuine biometrics.

\section{Engineering Problem}
Generic conversational assistance lacks direct access to the state visible on a wellness dashboard. Conversely, passing arbitrary or stale telemetry to an assistant makes fluent answers appear more reliable than their underlying data. The engineering problem is to combine local telemetry processing and wellness assistance while enforcing five core properties:
\begin{itemize}[noitemsep,topsep=1pt]
  \item a verifiable separation between genuine wearable observations and synthetic control telemetry;
  \item rejection of malformed, incomplete, simulated, or stale inputs prior to presentation;
  \item dynamic visual indication of link state, data source, and freshness;
  \item deterministic fallback operation with observable task timing and queue state; and
  \item bounded, context-grounded conversational feedback without clinical diagnosis claims.
\end{itemize}
This problem is constrained by prototype realities: the genuine pathway proves receiver-side records and bridge eligibility rules rather than an end-to-end cloud guarantee, while physical ESP32 sensing represents planned simulation rather than deployed hardware.

\section{Limitations of Unqualified Wellness Interfaces}
An interface can be technically misleading even when displayed metrics originate from legitimate sensors: heart rates may be historical rather than current, network packets may drop fields, or an interface may retain expired values indefinitely after disconnect. The developed application, named KINETIQ, treats arrival timestamps, value-change fingerprints, and freshness states as primary interface data, automatically blanking measurements when the offline threshold is reached. The same discipline governs conversational artificial intelligence: while context grounding conditions assistant responses on accepted snapshots, a grounding verdict does not establish clinical safety. The application is strictly a wellness-support prototype and does not provide medical diagnosis, treatment, or emergency monitoring.

\section{Objectives}
The implemented objectives focus on evidence separation and controllable operation:
\begin{enumerate}[noitemsep,topsep=1pt]
  \item Implement an observable native FreeRTOS control lane with activity commands, queue diagnostics, and synthetic telemetry;
  \item Ingest Huawei Health observations via an accessibility relay and authenticated local receiver without claiming a direct watch API;
  \item Define and enforce a shared eight-field telemetry contract prior to dashboard or assistant ingestion;
  \item Render transport link, source provenance, freshness, and data quality states visibly to the operator;
  \item Generate context-grounded wellness responses with an automated \texttt{PASS}/\texttt{FAIL} consistency verdict and offline fallback; and
  \item Document reproducible demonstration benchmarks, test boundaries, and simulated hardware scope.
\end{enumerate}

\section{Scope and Boundaries}
The ingestion receiver executes on the host laptop, binding to \code{0.0.0.0:8000} to accept authenticated HTTP POST payloads from the Android accessibility relay. Communication is verified across two routes: private Wi-Fi using the laptop's local IP, and offline USB using reverse port forwarding (\code{adb reverse tcp:8000 tcp:8000}), which routes the phone's loopback endpoint (\code{127.0.0.1:8000}) directly to the host receiver. Locally, an internal bridge queries \code{127.0.0.1:8000} and streams validated contract packets to the mirror dashboard application, which binds to loopback (\code{127.0.0.1:8777}). The bridge admits packets only when HR, $\mathrm{SpO_2}$, and steps are present, valid, non-simulated, and live under relay rules; stress is excluded from the mirror schema. The control lane processes console inputs \texttt{1} (Rest), \texttt{2} (Walk), \texttt{3} (Run), \texttt{b} (Fall), and \texttt{0} (Auto), providing diagnostic observability rather than hard real-time guarantees. Planned embedded hardware is evaluated in Wokwi simulation only.

\chapter{IMPLEMENTATION AND METHODOLOGY}

\section{Software Organisation}
The software architecture is organised into modular, cooperating subsystems designed for determinism, interface safety, and clear separation of concerns. The embedded FreeRTOS subsystem manages deterministic task execution, synthetic control generation, and real-time execution diagnostics. The shared validation subsystem enforces strict schema contracts, data ranges, and local ingestion protocols. The local web application hosts the wellness mirror interface, managing dashboard telemetry states on loopback endpoints, while the sensor-grounded AI and speech modules handle contextual guidance and local voice transcription without allowing unverified external data to modify display states.

\section{FreeRTOS Tasks, Queue, and Synchronisation}
The control node initialises an eight-element sample queue and a mutex for the shared control state, then creates console, sensor, classification, and telemetry tasks. The sensor task produces virtual sensor samples at 100 ms. The classification task consumes queued samples once per second and uses hysteresis to reduce rapid state changes. A higher-priority telemetry task publishes a one-second status payload. Standard output ownership is confined to the telemetry task, which prevents interleaved JSON fragments from multiple writers.

Timing diagnostics record intended period, measured period, maximum lateness, queue high-water mark, dropped events, and missed deadlines against a 120 ms lateness threshold. These figures aid reproducible host debugging rather than proving hard real-time scheduling guarantees on Windows.

\section{Genuine-Path Ingestion and Bridging}
The Android relay converts Huawei Health UI observations into a local JSON payload and transmits it via authenticated HTTP POST to the local receiver on the host laptop across the shared local Wi-Fi network (or via USB reverse port forwarding \code{adb reverse tcp:8000 tcp:8000}). The authenticated receiver validates bearer credentials, logs timestamps, and persists each accepted row with transport metadata. The bridge enforces an all-or-nothing policy: HR, SpO\textsubscript{2}, and steps must all exist, pass range checks, and be classified as live and non-simulated before forwarding to the mirror.

The following pseudocode captures the bridge decision without exposing application secrets or unrelated implementation detail:

\needspace{20mm}
\begin{lstlisting}[caption={Genuine-only bridge policy, simplified.},label={lst:bridge-policy}]
snapshot = read_latest_authenticated_relay_snapshot()
if snapshot.simulated or snapshot.freshness != "live": reject()
if missing(snapshot.hr, snapshot.spo2, snapshot.steps): reject()
if not in_range(snapshot.hr, 30, 220): reject()
if not in_range(snapshot.spo2, 70, 100): reject()
if snapshot.steps < 0: reject()

emit_to_mirror({timestamp, heart_rate, spo2, activity="unknown",
  motion_intensity=0, exertion=bridge_heuristic(...),
  steps, ppg_quality="good"})
\end{lstlisting}

The PPG-quality assignment is an upstream-completion proxy, not a signal-quality algorithm. The exertion field is a bridge heuristic. The reporting language therefore treats the bridge output as validated transport context with selected derived fields, not as a fully measured physiological model.

\section{Schema Validation and Dashboard State}
The web ingress parses incoming JSON and validates the eight required keys against Table~\ref{tab:telemetry-contract} boundaries, rejecting invalid packets without mutating the accepted snapshot. Freshness logic applies a 60\,s live interval, a subsequent 60\,s stale interval, and an offline blanking threshold at 300\,s, using snapshot fingerprints to distinguish unchanged repeated arrivals from transport dropouts.

\section{Grounded Assistance and Voice Route}
The assistant constructs local context from accepted telemetry and queries local Ollama \code{gemma2:2b}, reverting to a deterministic template when offline. Responses are bounded to 70 words. A rule-based verifier checks contextual mentions (activity, exertion, exact HR/steps, PPG qualification) and outputs a \texttt{PASS}/\texttt{FAIL} tag. The check is informative rather than fail-closed; speech synthesis continues regardless. Speech input is transcribed via faster-whisper \code{tiny.en} (\code{int8}), benchmarked at 0.48\,s on synthesized audio under local conditions.

\section{Launch and Fallback Procedure}
The reproducible operator route follows a disciplined sequence: (1) start the local web application on loopback port \code{8777}; (2) launch the authenticated receiver selecting either the genuine bridge or the native FreeRTOS control executable; (3) inspect dashboard source and freshness indicators; (4) transmit a fresh Huawei relay snapshot for genuine-path demonstration; (5) select the RTOS synthetic lane when transport is absent, preserving its control label; and (6) log console diagnostics for formal verification. The fallback retains operability, not equivalence: RTOS synthetic values cannot substitute for unavailable wearable observations.

\section{Hardware Simulation and Integration Status}
The Wokwi sketch models the embedded direction with task-oriented code and simulated inputs, supporting early pin and logic exploration. While the physical BOM and pin map support planned assembly, the final demonstration does not claim newly acquired ESP32 readings; no runtime validation should be interpreted as a completed physical sensor integration.
